> 版本：v0.4（2026-10-21，風格改為比照 ear.com.tw，加官網管理）　相關文件：[需求清單](需求清單.md)、[討論事項](討論事項.md)
> 本文的設計建立在 y1crm 現況上，包括 LINE 機器人、預約留言、.26 IIS 反向代理。標「待確認」的地方要先看[討論事項](討論事項.md)。
>

> - 預約改成直接寫進 `crm1.booking_requests`。資料庫帳號只有「新增指定欄位」的權限，讀不到任何 crm1 資料；原本規劃的 y1crm 內部 API 不做了，y1crm 停機時官網照樣能收預約。
> - 商品型錄透過資料庫檢視 `y1web.v_catalog` 讀取。

> **v0.3**：視覺改成 interton.com.tw 的風格（§11）；新增「聽力不求人」`/hearing-test`（§14）；產品頁加上機型與照片（§6.4）；預約排除週日。

## 1. 目標

1. 讓客人在網路上找得到門市、看得懂服務，並且**直接預約**。
2. 官網、LINE、y1crm 三邊**資料互通**。官網的預約和 LINE 的預約進同一個清單；活動、常見問題、門市資訊只維護一份。
3. 不增加店員負擔：內容在 y1crm 後台改，不用改程式。

### 三個原則

1. **公開網站讀不到客戶資料。** y1web 的資料庫帳號只能讀 `y1web` 資料庫（含型錄檢視），對 `crm1` 只能「新增預約」，連自己寫進去的預約都讀不回來。網站被攻破時，最多損失的是公開內容，外加被灌假預約。
2. **公開網站沒有登入功能。** 後台放在 y1crm 裡（「官網管理」選單），沿用 y1crm 現有的帳號和權限。對外少一個登入頁，就少一個被猜密碼的入口。
3. **預約後續由 y1crm 處理。** 客戶比對、通知店員、LINE 連動、前一天提醒都在 y1crm。y1web 只負責驗證格式、擋灌水、寫入一筆。
4. **服務隔離。** y1web 用專用系統帳號 `y1web` 執行（比照 TWIII 會員站），systemd 讓整個檔案系統唯讀，並遮住 y1crm、TWIII、aoi 與 `/mnt/raid1`。實測在服務環境內讀 y1crm 的 config.toml 會得到 Permission denied。

## 3. 技術選型

| 項目 | 選擇 | 理由 |
|---|---|---|
| 後端 | Python 3.12＋FastAPI＋uvicorn | 和 y1crm 相同，維護一套就好 |
| 頁面 | Jinja2 在伺服器端產生 HTML | 搜尋引擎讀得到；長輩的手機不用跑大量 JS |
| 前端 | 自寫 CSS＋少量原生 JS，不用框架、不用打包工具 | 頁面小、載入快、不用維護 node 工具鏈 |
| 字型 | 系統字型（蘋方、微軟正黑體、Noto Sans TC） | 不用下載字型檔，也不會把訪客 IP 送給 Google Fonts |
| 文章格式 | Markdown，用 markdown-it-py 轉換並**關閉原始 HTML** | 店員好寫，也不會被塞入惡意程式碼 |
| 資料庫 | 同一台 MySQL 8，新增 `y1web` 資料庫，collation `utf8mb4_unicode_ci` | 沿用既有教訓：collation 不一致時 JOIN 會出錯 |
| 圖片 | 上傳時用 Pillow 縮成 3 種寬度並轉成 WebP | 長輩多用 4G，圖片是頁面大小的主要來源 |
| 服務 | systemd `y1web.service`，port **8006** | 8004 是 y1crm、8005 是 TWIII 會員站，8006 目前沒有被占用（2026-10-21 用 `ss -ltn` 查過） |

### 為什麼不用 WordPress

interton 用 WordPress。我們不用的理由：

- 要多維護 PHP 和 WordPress 外掛的安全更新。
- 預約資料要再寫一層才能進 y1crm。
- WordPress 會多一個對外的後台登入頁。

## 6. 資料設計

### 6.1 `y1web` 資料庫（公開內容，沒有個資）

| 資料表 | 主要欄位 | 用途 |
|---|---|---|
| `web_posts` | id, kind(article/event/product), slug UNIQUE, title, summary, body_md, cover_media_id, category, status(draft/published), publish_at, start_date, end_date, sort, extra JSON, updated_by, updated_at | 文章、活動、產品共用一張表。活動用 start/end 自動上下架；產品的品牌和款式放 extra |
| `web_faq` | id, category, question, answer_md, sort, status, show_on_line, use_for_ai | 官網、LINE、AI 共用。`use_for_ai` 預設關閉，**含價格的題目一律不給 AI** |
| `web_settings` | k PK, v JSON | 門市資訊（名稱、地址、電話、營業時間）、首頁標語、主視覺 |
| `web_media` | id, rel_path, alt, width, height, created_at | 上傳的圖片，alt 必填 |
| `web_stats_daily` | day, path, views（P2） | 簡易流量統計，不記 IP |

DDL 寫在 `scripts/schema_web.py`，可以重跑（沿用「DB 設定要進版控」的慣例）。

### 6.2 資料庫帳號

已由 `scripts/setup_db.py` 建立（可重跑），實際權限：

| 帳號 | 權限 | 誰用 |
|---|---|---|
| `y1web_app`@localhost | `y1web.*` 只能 SELECT（含 `v_catalog`）；`crm1.booking_requests` 只能 INSERT 這 10 個欄位：contact_name, phone, req_date, req_hour, note, source, kind, address, link_code, link_expires | 公開網站 |
| y1crm 現有帳號（root） | 全部 | 建表、種子內容、官網管理後台（M2）、LINE 機器人 |

2026-10-21 實測：`y1web_app` 查 `crm1.products` 的售價、`crm1.customers`、`crm1.booking_requests` 都被拒（1142）；查 `v_catalog.list_price` 會回「沒有這個欄位」（1054）。

`v_catalog` 只開放這些欄位：id, brand, model_name, spec, category, ha_form, ha_tech_level, ha_channels, ha_battery, ha_bluetooth, ha_tcoil, ha_ip_rating, ha_fit_levels, compatible_models，條件是 `is_active=1`。備註欄有「一對銷售價」這類字，所以也不開放。

### 6.3 `crm1` 的改動（已上線）

`booking_requests` 新增 5 個欄位：

| 欄位 | 型態 | 用途 |
|---|---|---|
| `source` | ENUM('line','web')，預設 'line' | 預約來源 |
| `kind` | ENUM('store','home')，預設 'store' | 門市預約或到府服務 |
| `address` | VARCHAR(200) NULL | 到府地址 |
| `link_code` | CHAR(6) NULL，UNIQUE KEY `uq_bk_link_code` | LINE 預約碼 |
| `link_expires` | DATETIME NULL | 預約碼期限 |

另外：

- `line_user_id` 原本就允許 NULL。
- 既有的 LINE 預約全部是預設值（line／store），舊程式不受影響。
- 「聯絡我們」的一般詢問還沒有做，目前聯絡頁只放電話、LINE 和預約入口。

## 7. 預約流程（官網 → y1crm）

程式在 `app/booking.py`、`app/main.py`。

1. 客人填寫表單：
   - 門市預約（`/booking`）：稱呼、電話、日期、時段、需求（選填），並勾選同意個資說明。
   - 到府服務（`/home-visit`）：同上，多一個到府地址。
2. y1web 檢查以下項目，任何一項不通過就退回表單並標出欄位：
   - **規則和 LINE 預約相同**：明天起 14 天、09–18 整點、電話至少 7 碼。規則寫在 `app/booking.py` 開頭，要和 y1crm `api/line_bot.py` 一起改。
   - 表單簽章：打開頁面不到 3 秒就送出，或停留超過 2 小時，都要重送。
   - 隱藏欄位有值就判定為機器人：畫面照樣顯示「已收到」，但不寫入。
   - 次數限制：同一 IP 每小時 5 筆、同一電話每天 3 筆。
   - 重複送出：30 分鐘內同電話、同時段、同類型的送出，回傳同一個預約碼，不重複寫入。
3. 寫入 `crm1.booking_requests`，`source='web'`，同時寫入 `kind`、`address`、6 碼預約碼與期限。
4. 完成頁顯示預約內容和預約碼，以及「加 LINE 收確認和提醒」（見 8.2）。頁面設成不快取。
5. 店員在 y1crm「預約留言」頁看到這筆，標「官網」，到府服務另外標「到府」並顯示地址。
6. 客戶比對：手機號碼剛好對到一位客戶時，只顯示「可能是 ○○○」。店員電話確認是本人後，按「掛上」才寫入 customer_id（`PUT /api/bookings/{id}/customer`）。官網沒有身分驗證，任何人都能填別人的號碼，所以不自動掛。

記錄檔只寫稱呼的第一個字、電話末 3 碼與預約碼。

## 8. LINE 整合設計

現況（y1crm 已經有的功能）：

- 官方帳號 @021tpjrz，webhook 在 y1crm。
- 圖文選單 6 格：預約、查詢預約、常見問題、最新活動、門市資訊、找客服。
- AI 自動回覆。
- 店員配對綁定客戶。
- 預約前一天 18:00 自動推播提醒。

### 8.1 加好友（B1）

- 網址：`https://line.me/R/ti/p/@021tpjrz`
- 手機：點了直接開 LINE。
- 電腦：跳出 QR Code，用手機掃。
- 按鈕都先經過 `/line?from=頁面` 再轉址，用來統計各頁帶來多少好友（P2）。

### 8.2 預約後接 LINE（B2）：不用 LINE Login 的做法

```
官網預約完成頁
  └─ 按「加 LINE 收提醒」
       → 開啟 https://line.me/R/oaMessage/@021tpjrz/?預約碼%20K7Q2XM
       → LINE 已經填好「預約碼 K7Q2XM」，客人按傳送
            → y1crm webhook 比對預約碼（有效期限內、這筆還沒連 LINE）
            → 這筆預約寫入 line_user_id，預約碼作廢
            → reply「已收到您 10/25（六）10:00 的預約，前一天會提醒您」（reply 免費）
            → 之後的前一天提醒、確認前往按鈕，全部沿用現有排程
```

已實作，程式在 y1crm `api/line_bot.py` 的「官網預約碼」段落，2026-10-21 上線：

- **預約碼的判斷排在「預約」關鍵字和 AI 自動回覆之前。** 現在只要訊息含「預約」，機器人就回預約連結；如果順序反了，客人傳預約碼會收到一張新表單。
- 預約碼 6 碼，從不易混淆的字元中隨機產生（不用 0/O、1/I）。期限是 7 天或到預約日當天結束，取較早者。
- 連上之後，這個碼只對那個 LINE 有效：同一人重傳會收到同樣的確認，別人拿來用一律無效。
- 同一個 LINE 輸錯 5 次，1 小時內不再比對。
- 只傳 6 個英數字、沒寫「預約碼」也接受；但如果對不到，就當一般訊息交給原本的流程（AI 或提示）。
- 這個流程只把**這一筆預約**連到 LINE。如果這個 LINE 已經由店員綁定客戶，會順便把預約掛到那位客戶；否則**不會**把客戶資料綁到這個 LINE。
- 進出的訊息都記進 `line_messages`，CRM 對話頁看得到。
- 前一天提醒：到府預約的提醒文字改為「到府服務時間」。
- 完成頁在手機上有兩個按鈕：①加入 LINE 好友 ②傳送預約碼。電腦上則顯示兩個 QR Code。這是因為推播（提醒）只能送給好友，必須先加好友。
- **待實測**：用真的手機點「傳送預約碼」，確認 iOS 和 Android 的 LINE 都會帶入文字。

### 8.3 活動、FAQ、門市資訊共用（B3–B5）

- LINE 的「最新活動」改從 `y1web.web_posts` 讀取：今天落在起訖日期內、已發佈的活動，最多 3 則，每則附官網連結。沒有活動時，顯示目前那句「目前沒有活動」。
- 常見問題按鈕改讀 `web_faq` 中 `show_on_line=1` 的題目。
- AI 客服知識庫加入 `use_for_ai=1` 的題目。**輸出端的價格攔截維持不變。**
- 門市資訊改讀 `web_settings`；資料庫讀不到時退回程式內的預設文字，避免 LINE 回不了訊息。
- 圖文選單 6 格都不動，不用重新佈署。

### 8.4 LINE 預約表單併入官網（B6，P2）

- LINE「我要預約」改發 `官網/booking?t=一次性token`。
- 已綁定的客戶自動帶入資料，送出後 `source='line'`。
- 舊的 `/lp/booking` 保留一段時間後再移除。

### 8.5 不做的事

- **網站不做 LINE Login／LIFF。** 這兩樣要另外申請 LINE Login channel，且要放在同一個 provider 底下才拿得到相同的 userId。客人也要多按一次同意。8.2 的預約碼已經能達到「連到 LINE 收提醒」的目的。
- **官網不放 AI 聊天視窗。** 想問問題的人導到 LINE，由現有 AI 客服和店員回覆，GPU 也只服務一個入口。
- **新預約不用 LINE 推播通知店員。** 推播每月只有 200 則免費額度，而且店員不一定是官方帳號的好友。通知店員改用 y1crm 紅點，見討論事項。

## 9. 對外上線

- 沿用目前的入口：.26 Windows IIS 已經接管 WAN:443，上面有多個正式服務。
- 做法：在 IIS **新增一個站台，綁定新網域**，用 ARR 轉到 `http://192.168.1.88:8006`。
  - TLS 憑證用 win-acme 申請 Let's Encrypt，自動續約。
  - 既有的 webhook 和 `/lp/` 規則**完全不動**。
- y1web 用 uvicorn `--proxy-headers --forwarded-allow-ips=192.168.1.26`。只有 .26 送來的 `X-Forwarded-For` 才採信，次數限制才能依真實 IP 計算。
- 已知限制：路由器沒有 hairpin NAT，**在店內 WiFi 打不開對外網址**。驗收要用手機 4G。長期解法是內網 DNS 分流，見討論事項。
- 網域確定之前，可以在區網用 `http://192.168.1.88:8006` 開發和展示。

## 10. 安全與個資

| 項目 | 做法 |
|---|---|
| 權限隔離 | 公開網站的資料庫帳號只讀 `y1web`；內部 API 要 token，且只接受本機呼叫；y1web 用非 root 帳號執行 |

## 14. 聽力不求人（`/hearing-test`、`static/js/hearing-test.js`）

- **流程**：同意說明 → 播放 1 kHz 參考音、請客人把音量調到「像平常說話」→ 左右耳試聽確認耳機沒戴反 → 右耳、左耳各測 1k、2k、4k、6k、8k、500、250 Hz → 結果。
- **方法**：簡化的 Hughson-Westlake 上升法。從 30 dB 開始（沒聽到每次 +10 找到第一次聽到），之後聽到 −10、沒聽到 +5，同一音量在上升時聽到 2 次就是閾值；每頻率最多 16 次。測試音是 3 短聲，間隔隨機 0.6–1.6 秒；聲音結束後 1.3 秒內按都算聽到；沒聲音時按會記下來，太多次會在結果提醒。
- **音量對應**：參考音 gain 0.08＝60 dB HL；各頻率加 TDH-39 基準等效閾值和 1 kHz 的差（ANSI S3.6）。最大 gain 0.9，所以各頻率可測上限約 60–80 dB HL，超過顯示「≥上限」。耳機沒校正，全程標示「僅供參考」。
- **結果**：右 O 紅、左 X 藍的聽力圖（−10–100 dB，分級色帶）、各頻率表、兩耳 500–4k 平均與分級（≤25 正常、≤40 輕度、≤55 中度、≤70 中重度、≤90 重度）。兩耳平均差 ≥15 dB 或 2 個頻率差 ≥20 dB 會提醒就醫；頁面也提醒突發性聽損要直接就醫。
- **個資**：結果只在記憶體；按「帶著結果預約」才把摘要寫進 sessionStorage，預約頁自動放進備註欄，客人可以刪掉。預約完成頁會清掉。
- **驗證**：用無頭 Chromium 模擬聽者（設定好 14 個閾值、計時器加速 10 倍）跑完整流程，量到的 14 個值和設定完全相同，「聽不到」正確顯示 ≥60，帶結果預約正常。實際長度約 5–8 分鐘。
